# 06 · 1080p 母版：只重出视频，其余全部复用

## 复用原则

- **只重出视频镜头**：从画布上找到原 480p 节点，复制它的首尾帧、提示词、时长、声音开关，只把清晰度改成 1080p、模型换正式版，新节点 `镜HD-<镜号>`。不重新生图、不改提示词。
- **已有的高清镜头直接用**。
- **音轨全部复用**：组装时直接取 480p 片段的原声，镜头裁到 480p 时长（慢放过的镜头按同比例慢放），这样镜头起点、混音、字幕时间和 480p 完全一致。
- **同期声镜头**：用 audio2video，把原片那句同期声当输入驱动口型——口型和原声对得上，字幕时间不用动。输入过不了合规时退回首尾帧生视频，用新片自带音轨，字幕按新起声平移，列进清单。
- 1080p 只出母版给正式版和预告片；Web Demo 继续用压缩过的 480p。

## 出片脚本的必备能力

| 能力 | 原因 |
|---|---|
| 分片 `--shard i/N`、场景清单 `--scenes`、排除 `--exclude` | 多 worker、多会话分工 |
| 每镜 O_EXCL 文件锁（写 pid，死锁可接管） | 多个会话跑同一批镜头也不重复出片 |
| `STOP` 文件：遇「算力不足」写入并退出，其他 worker 开下一镜前看到也退出 | 一处没钱，全部停下 |
| 瞬时错误就地重试：5xx / 超时 / 连接重置，30 → 90 → 180 秒退避，最多 3 次 | 本次挂起过 3 镜 |
| 节点已存在但没写回 URL：重跑原节点，不重建 | 避免撞名和重复扣费 |
| `audit`：复核「派生片」记录，画布上有原节点的撤销误判 | 旧版遇瞬时失败会把镜头误记成派生片，永远不会出片 |
| 追加写的结果日志（一行一镜，同 id 以最后一条带 URL 的为准） | 断点续跑、可审计 |

## 判错要精确

- 「节点不存在」只认平台的原文报错（如「未找到展示名或节点」）；其他错误一律当瞬时错误重试或记失败。把 request fail 当成「不存在」，就会把有原节点的镜头误记成派生片，永远不再出片。
- 「合规检测未通过」重跑也一样，不是瞬时错误：直接走降级方案（audio2video → frames2video）。

## 并发

- 服务端有实际并发上限（本次实测约 4 路）：超过后单镜耗时从约 190 秒涨到 300–750 秒，总吞吐不变（约每小时 75–95 镜）。
- 试点 2 个场景（含一个同期声镜头）确认参数和耗时，再扩到上限。
- 总吞吐卡死时，**先保金线**：金线占满并发，支线降到 1 路；金线跑完自动把支线升回上限（写成后台守候进程，别靠人工通知）。
- 本地组装（ffmpeg）最多 2 路，机器负载高时更少。
- **只降部分分片、不打断在跑的镜头**：起一个 `sleep` 占位进程，用它的 pid 预先锁住要停的分片剩下的镜头；那些分片出完手上一镜就自然退出。升路时 kill 占位进程，锁自动失效。（STOP 文件会停掉所有 worker，不适合降路。）

## 组装

- 守候进程：某场景镜头到齐就组装一段；**一直守到全部完成**，不要设「组装 N 段就停」，长时间没新镜头也别退出（空闲阈值放宽到几小时）。
- 某镜被标成派生片却找不到高清文件时，跳过这个场景并记进质检表，不要用低清放大顶替。
- 有镜头出了新高清版本时，所属场景自动重组。
- 每段组装后抽帧和 480p 对比：构图、主角不露嘴、时长与镜头起点。**只要求首尾帧构图、镜头起点、时长一致**；同一组首尾帧重新生成，中段动作本来就不会逐帧一致，记录即可，不当缺陷返工。镜头起点比较用容差（`abs < 0.01`），不要 `round(…, 2)`。
- **用原混音脚本出 1080p**：重跑各段原脚本的 mix 步骤、拦截构建函数改输出 1080p，镜头表和混音参数不重写。但原脚本在构建之后还会写总表、引擎、自己的清单、压掉 480p 成片——只拦构建不够：拦截的构建里出完 1080p 立刻抛异常，让原流程停住；再给文件写入加守卫，凡写总表、引擎、清单、480p 目录一律报错。
- **找产出脚本**：按「清单里 file 一致 → 各脚本的段落表」依次查；老片可能没进任何批次清单，改过键名的插入片要从文件名反推。
- **修正批次优先**：重出的镜头先只写进 `media-fix<N>.json`，主会话合并前组装器仍按旧清单组装，会把问题镜头装回去。组装器查产出时让 fix 清单优先；fix 脚本声明自己供片的镜头集合，这些镜头不等高清日志。
- **换守候进程不打断组装**：只对守候进程发 SIGTERM，它起的组装子进程会继续跑完；新守候先等到没有组装子进程在跑再开始，避免同一场景组装两次。

## 回报节奏

只在三种情况打扰用户：出错 / 算力不足、每完成约 1/4、全部完成（附总段数、总体积、质检遗留）。
